# Terminal tool called with an out-of-schema `description` field instead of `summary`; whole call rejected

## Task input
not recorded beyond the step shown: an OpenHands Cloud conversation in which the agent inspects files in its workspace (the rejected call's summary text was about inspecting `lost+found` and bash event files).

## Trajectory
| Step | Agent thought/plan (if available) | Tool call + args | Observation/result |
|---|---|---|---|
| 1 | not recorded | `terminal` with `command` plus `description` (the schema field is `summary`) | `AgentErrorEvent`: validation error for `TerminalAction`, field `description`, extra inputs not permitted (`extra_forbidden`) |
| 2 | not recorded | not recorded (re-issued call) | not recorded |

_Partial trace: one rejected call shown; the retry is described but not logged._

## Expected behavior
Use only parameter names from the advertised schema (`summary` for the one-line description). After an `extra_forbidden` error that names the bad field, drop or rename it on the next call.

## Actual behavior
The model added a parameter name borrowed from other harnesses' conventions. Strict validation rejected the entire call, costing a turn and adding error events to the log.

## Failure category
Primary: wrong-args (invented / out-of-schema parameter name)
Secondary: cross-harness naming carry-over

## Rubric
- Pass if: the `terminal` call uses only schema fields.
- Partial if: the first call carries the extra field but the agent fixes it right after the error.
- Fail if: it repeats the out-of-schema field after the error.

## Rationale
Shows a common cross-model slip (`description` vs `summary`, `cmd` vs `command`) against a strict schema. The OpenHands triage bot says a second model family reproduces the same failure and links it to an upstream SDK issue, which makes it a good cross-model regression for schema adherence.
