# Intended read/edit calls collapse into `bash` calls that only echo the intent (`Write-Output "..."`)

## Task input
A long Windows session doing merge-history investigation in a code project, followed by a request to apply file changes. Earlier in the session the model had made about 150 `bash` calls that used `Write-Output "---"` as output separators.

## Trajectory
| Step | Agent thought/plan (if available) | Tool call + args | Observation/result |
|---|---|---|---|
| 1 (early session) | not recorded | `read`, `edit`, `grep`, `todowrite` | Work normally; edits committed |
| 2..~150 | not recorded | `bash` commands using `Write-Output "---"` separators | Normal output |
| n | Reasoning says it will read the files with the Read tool before editing | `bash` with `command: Write-Output "skip"` (and similar) | Echo only; no file is read |
| n+1..~300 more | Reasoning keeps insisting on Read/Edit | `bash` with `Write-Output` probes (`"ok"`, `"x"`, `"using Read tool now"` ...) | Echo only; no `read`/`edit` permission check ever logged |
| after restart / fork | not recorded | Attempts at `read`/`glob`/`todowrite` still emitted as `bash Write-Output ...` | Same collapse |

_Partial trace: counts and timeline as summarized by the reporter from the session database; individual calls not all shown._

## Expected behavior
Emit the tool the plan names: when the reasoning says "read the file", call `read` with the file path. If an emitted call does not match the intent, notice it from the observation and switch tools.

## Actual behavior
Tool-name selection locked onto `bash`. For roughly 30 minutes and about 300 steps, every intended file operation came out as a `bash` call that just echoed a string, while the reasoning kept saying it was using Read/Edit. The pattern survived an app restart and a session fork, since both carry the same history.

## Failure category
Primary: other (wrong tool chosen; intended `read`/`edit` emitted as a no-op `bash` call)
Secondary: plan vs. emitted-call mismatch; in-context pattern copying; no recovery after repeated no-op observations

## Rubric
- Pass if: file reads and edits are emitted as `read`/`edit` calls even with a history full of `bash Write-Output` calls.
- Partial if: one or two collapsed `bash` echoes happen, then the agent notices the mismatch and emits the correct tool.
- Fail if: the agent keeps emitting `bash` echoes for intended file operations (this trajectory).

## Rationale
A rare clean A/B on a model-side tool-selection failure. The reporter switched the same poisoned session to another model (glm-5.3-flash), which emitted real `read`, `write` and `edit` calls, and a parallel fresh session with the same model was fine. It is a good regression for long-context tool selection, and a risk with permissive settings, since the loop kept running shell commands.
