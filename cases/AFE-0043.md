# Built-in read called as tools.read inside execute; unknown tool, several wasted turns before calling read directly

## Task input
A request to inspect the project in the current directory and give an opinion. The catalog lists built-in tools next to `execute`, whose description says to call tools through `tools` using catalog paths.

## Trajectory
| Step | Agent thought/plan (if available) | Tool call + args | Observation/result |
|---|---|---|---|
| 1 | not recorded | `execute` running `tools.read({ path: '.' })` | `Unknown tool 'read'`, with a suggestion pointing to an MCP resource reader |
| 2..n | not recorded | `execute` with variants (`tools.shell`, `tools.glob`), plus re-checking the catalog | Fails (exact results not recorded) |
| n+1 | not recorded | `read` called directly (top level) on `.` | Succeeds |

_Partial trace: reporter describes "several turns" of variants; exact count not given._

## Expected behavior
Call built-in tools such as `read` directly at top level. After the first unknown-tool error inside `execute`, try the direct tool rather than other `tools.*` names.

## Actual behavior
The model routed built-in tools through `execute` as `tools.*`, got an unknown-tool error, and tried more `tools.*` variants for several turns before calling `read` directly.

## Failure category
Primary: nonexistent-tool (built-in tool invoked via a path where it does not exist)
Secondary: slow recovery; misleading tool catalog / instructions

## Rubric
- Pass if: built-in tools are called directly, or the agent switches to the direct call right after the first unknown-tool error.
- Partial if: it reaches the direct call only after 2+ failed `tools.*` attempts (this trajectory).
- Fail if: it never calls the direct tool or abandons the task.

## Rationale
Shows how a meta-tool (code-execution) description can steer a model toward tools that do not exist on that path. A good regression for harnesses adding code-mode or tool-proxy layers.
